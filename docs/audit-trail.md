# General audit trail

Settings > Audit trail and `python manage.py query_audit --member <app-member-id>` review the same authorized rows, ordered by newest UTC timestamp then event UUID, 50 per page. Use `--page`, `--action`, `--actor` (app member ID), `--source`, `--date-from` and `--date-to` (inclusive UTC dates). The command is read-only JSON, suitable for an offline reader; choosing a member does not grant a larger operator audience. Web responses use no-store. Do not save query output to public places.

Recorded actions (the coverage matrix is `ACTION_SPECS` in `finance/audit_models.py`; `tests/test_audit_coverage.py` exercises every entry and its alternative entry paths):

| Area | Actions | Audience |
| --- | --- | --- |
| Account lifecycle | created (including through SimpleFIN), renamed, shared, unshared, share mode changed, ownership changed (co-owned account passes to the successor when its owner leaves), archived, debt terms changed, loan pairing changed, deleted | The account's current access; deletion keeps only a metadata event for the private owner or household at deletion time |
| Household access | household created (first member), invitation created, invitation accepted, member left | Current household members |
| Sign-in and sessions | Google connected/disconnected, password added/changed/removed (including recovery-code reset), passkey requirement changed, one session revoked, other sessions revoked, privacy policy accepted/declined | The acting member only |
| Connections | SimpleFIN connected/disconnected/links or cut-over changed; AI harness connected/disconnected, AI key connected/replaced/disconnected, AI defaults changed, shared local-model choice changed | The acting member only |
| Host offers | local-model offered to the household or for chat, plan links offered | Current household members see the setting name only, never the host's credentials or usage |
| Notifications | alert preferences, notification address/enabled, bill calendar settings | The acting member only |

Events record action enums, opaque target IDs, the initiator (`actor`) and, where different, the `affected_member`; the CLI and page show both. A member leaving records the leaver as both. Operator eviction records operator kind, the evicted effective/affected member, and optionally a separately declared operator member; it never names the evicted member as the initiator. Automatic loan-pairing clears caused by sharing or unsharing are covered by the sharing event, not a separate pairing event. Only successful state changes are recorded: no-op saves, denied, stale-authentication and invalid requests append nothing, and sign-in failures stay in the personal security events. Field lists name changed settings only (for example `alert_toggles`, `thresholds`, `account_links`, `cutover`), never values, emails, names, dates, amounts or secrets.

This trail has no backfill and does not claim coverage beyond the table. Correction history, sign-in/security records, import provenance and AI usage remain separate and are not copied. Later coverage must extend typed action/target enums, `ACTION_SPECS` and explicit append calls; request/download events must describe only what is known (for example export_generated does not prove delivery).

Each event contains a generated UUID and UTC time, enumerated action/outcome, trusted actor kind and nullable member/effective member references, target type and opaque app ID, audience references, source, UUID correlation/run ID, allow-listed changed field names and a SHA-256 checksum. There is no free-form payload, before/after values, actor name, amount, description, URL, raw row, credential or AI text. Correlation IDs must be UUIDs generated in trusted code, never arbitrary request headers. Sources and actors are supplied by trusted callers, never browser input. Use `append_event` inside the authorized action's database transaction, after the changed fields have actually changed. System callers supply their truthful scheduler/operator kind and the effective member whose access authorized the target.

For a surviving account, all its events follow current account authorization, including archived accounts. Only deletion events snapshot a private owner or household; earlier private history stays with an account that later becomes co-owned, and unshared history is not tied to a former household. The actor alone gains no access. Unsharing or membership exit revokes household access immediately, including counts and filters. On permanent account deletion, prior general events are removed; only metadata-only deletion events remain for the private owner or current members of the household at deletion. After member-data deletion, the member's personal events and private-account events disappear and retained household actor/effective/affected-member references become null. If the household itself is deleted its audit audience goes too.

`AUDIT_RETENTION_DAYS` defaults to 90 and `AUDIT_PURGE_BATCH_SIZE` to 1000 (both positive). The daily background pass calls the bounded purge once; expired rows above its batch cap await subsequent daily passes. Retention and account/member/household deletion are the only application cleanup exceptions. No event edit/delete API, form or admin registration exists; the append-only model/queryset rejects ordinary saves, updates, bulk inserts and deletes. Database administrators and the machine owner remain trusted; this is not tamper-proof storage. Checksums cover immutable event metadata, excluding visibility and actor references deliberately changed by deletion/anonymization. The CLI reports checksum validity.

A normal action and its event commit/roll back together. If the audit insert alone fails, its nested transaction rolls back, the action continues, the UI displays a generic warning and the operator receives an ERROR-level "Audit write gap" log. Jobs/CLI report the same generic log. Warnings and gap reports run only after the enclosing action commits; a later action rollback discards them. Database error text and parameters are never included. The missing event cannot be recovered automatically; investigate the database and record the operational gap privately. Never retry an action that already succeeded just to obtain an event. Invalid metadata is a programming error, not this fallback.

The server clock supplies event times; UUID tie-breaking gives deterministic ordering, not causality or a guarantee against clock drift. Monitor the host clock. Committed rows survive restarts and are included in ordinary database dumps. Restoring an older dump rewinds the trail and removes later events, like other application data. There is no guarantee of retention across restores. Synthetic dump/restore and restart verification belongs on disposable test databases only.

## Financial workflow coverage (#273)

Owner decisions: all listed actions are covered; `tags_changed` records a transaction's tag membership change without names; ordinary note edits have no event (#98); a committed import with no new rows records one `import_no_new_rows` event; every download records `download_prepared`. Retention, visibility, deletion and write-failure behavior are exactly those above.

Each row of the matrix is an explicit `record(...)` call inside the action's own transaction, in the service function rather than the view, so every entry path (UI, CLI, chat confirmation, automatic rules) shares one hook.

| Area | Action (target type) | Audience | Notes |
| --- | --- | --- | --- |
| Import | `import_committed` (import_batch), `import_no_new_rows` (account), `import_undone` (import_batch) | account | Metadata: batch ID, source `format` enum, new/duplicate/invalid/removed counts. Undo names the undoing member. No file name, hash or row content. SimpleFIN sync is outside this slice. |
| Manual entry | `record_created` / `record_deleted` (transaction) | account | Deletion references the existing correction-history ID. |
| Balances | `record_created` / `record_edited` / `record_deleted` (balance) | account | Changed field names only (`date`, `amount`, `contribution`, `note`); same-date upserts are edits. |
| Budgets | created, edited, archived, restored, `rollover_toggled`, rollover reset (`record_edited`, `rollover`, history ID) (budget) | household for household budgets, else the owner | |
| Planned items, goals | created, edited, enabled/disabled, completed, archived/restored (planned_item, goal) | as budgets | A wishlist import records one created or edited event per changed goal; changed field names include `priority`, `dependency`, `time_sensitive`. The household savings buffer records `record_edited` on a `setting` with field `buffer` for the household. |
| Categories, tags | created, renamed, archived (category, tag) | household | |
| Saved CSV mappings | created, edited, archived, deleted, `default_changed` (csv_mapping) | household; default changes follow the account | |
| Rules | created, edited, enabled/disabled, `rule_applied`, `rule_reversed` (rule) | household or owner | Applying records one aggregate event with the application ID and row count; automatic application after import uses source `rule`. A former household member reversing rows on their own account is audited privately. |
| Recurring | confirmed, dismissed, merged (`source_id`, `surviving_id`), added, removed, canceled, resumed, price acknowledged (recurring) | the member | |
| Corrections | `transaction_corrected` (transaction) | account | One per category/refund-link history row written by a direct action, with `history_id`. Splits, unsplits and refund links appear through their history rows. Transfer confirm/dismiss/undo use `record_enabled`/`record_disabled` with field `kind`. |
| Bulk edit | `bulk_applied` / `bulk_undone` (account) | account | One event per affected account with a row count; the event correlation ID is the existing bulk-undo UUID and source is `bulk`. Notes are never named. |
| Chat | any of the above | as above | Source `chat_confirmation`, metadata `proposal_id`, a generated operation UUID as correlation ID, the approving member as actor. Events outlive the conversation and proposal. |
| Receipts | `receipt_attached`, `receipt_removed` (receipt), `download_prepared` | account | Metadata: receipt ID and transaction ID, never bytes or file names. |
| Downloads | `download_prepared` (export) | the member | `export_kind` is `data_zip`, `year_end_csv` (with `section`), `transactions_csv` or `receipt`. Records that a response was prepared, not that it arrived. No year or filter values. |

Audience rules are the account's current access for account-bound targets; a household's current members for household-owned rows; and the member alone for private rows. A budget, goal, planned item or rule that changes scope is audited under its new audience. Metadata is a closed set of integer IDs/counts, enum strings and UUIDs (`audit_models.METADATA_*`); anything else is rejected without echoing the value. Changed field names are the allow-listed `CHANGED_FIELDS`. Events from internal restores (a counterpart leg the actor cannot see) are never written for a hidden account.

No-op writes, denied requests and rolled-back actions record nothing. Import throughput is unchanged: an import writes one general event plus one per winning automatic rule, never one per row.

## Scheduled work and operator maintenance (#274)

`operation_outcome` is a typed action with an allow-listed `operation` enum. Trusted execution context propagates the initiating actor and run UUID to nested #272/#273 events. Default UI/job/CLI sources follow that initiator; explicit rule, bulk and chat workflow sources remain distinguishable. The web never accepts actor, operator declaration or run context. `--operator-member <Person ID>` on the seven audited commands is a validated **declaration by the trusted host operator**, displayed separately from the authenticated actor. Omit it for operator (unattributed); OS identity is not collected. Background daily commands explicitly run as scheduler/job, while the same command run manually is operator/CLI. An effective member identifies the access used, not the human initiator.

| Operation | Recorded transitions | Audience / linkage |
| --- | --- | --- |
| SimpleFIN | One connection outcome per permitted sync, successful imported count or fixed provider/access/import failure enum | Connection owner only, connection ID and run UUID; UI requesting member, CLI operator or scheduler. Inner import savepoint failures keep the failure outcome and roll back imported/domain rows. Rate-limit and permission rejections produce no successful event. |
| AI jobs | New-session claim, stale recovery claim, failed retry attempt, final success/failure | Requesting member only; job ID, attempt and persisted run UUID. A new inference attempt receives a new UUID. A stale recovery claim has its own UUID and links the original inference attempt through `operation_id`; it spends no new inference attempt. Ordinary poll-only resumes retain the attempt and add no claim/outbound event. |
| Inference | Start before an actual outbound request and its normalized result | Requesting member only; connection ID, effective credential owner, provider/backend/feature enums; result references the existing `AiUsageEvent` ID rather than copying tokens/text. Poll-only resumes, decrypts, discovery, status checks and warming add no inference event. |
| Chat | Claim/start, conditional final reply, stale failure | Conversation member only; turn ID and stable claim/turn UUID. Only the runner holding the claim records a committed reply. Replies/text never enter the audit event. |
| Monthly reviews | Generation/regeneration after facts are stored; unchanged reads append nothing | Member only; review ID, inherited run UUID. Facts and review month are not stored in the event. |
| Alerts / email | Inbox creation, one attempted email outcome with a bounded alert count | Inbox follows account access when bound to an account, otherwise recipient-only; email summaries are member-only and never include addresses, titles, bodies or recipient lists. SMTP success means accepted by the sender, not proof of inbox receipt. |
| Operator commands | Start and outcome; nested domain events reuse the run UUID | Global metadata journal for `seed_first_user`, `evict_household_member`, `delete_member_data`, `publish_privacy_policy`, `rebuild_transfer_pairs`, `sync_simplefin`, `generate_monthly_reviews`; personal transfer rebuild outcome; existing household/account events keep their audiences. Seed recovery codes remain console delivery only. |
| Daily cleanup / alerts | One start/outcome per bounded audit retention pass and daily alert/cleanup pass | Global journal contains no target IDs or cross-member counts; individual member outcomes remain in the database trail. |
| Shell maintenance | Start/outcome for backup, off-site upload/prune, restore, restore check | Protected global journal, fixed operation/outcome enums, UUID correlation, UTC timestamp, actor kind/source and checksum only. No filenames, configuration paths, encryption keys, URLs, arguments or subprocess output. |

### Deploying and reading the journal

Compose binds `${BACKUP_DIR}/audit/application` to `/operator-audit` in app/background and `${BACKUP_DIR}/audit/maintenance` in backup. These directories are outside database and receipt volumes. The two directories separate the app user from the backup root user. Provision the application directory writable by the container's `app` UID/GID and restrict the parent/host directory to the trusted operator; on Windows restrict its NTFS ACL to the operator. The writer enforces 0700 directories and 0600 files on POSIX. No changes to an existing deployment, container, volume or backup are needed to develop/test this feature. Locally set `OPERATOR_AUDIT_DIR` to a protected writable directory before running an operator command.

Review is read-only and owner-only through the host filesystem (no new web page):

```sh
python ops/backup/audit_journal.py --query --directory /protected/application
python ops/backup/audit_journal.py --query --directory /protected/maintenance
```

The reader verifies checksums and emits a generic warning instead of unverified/malformed content. Daily JSONL shards rotate on successful appends: shards older than 90 days are deleted; an idle installation may retain older shards until the next write. Files are not copied into database dumps. The operator may include their directory in a protected host backup; restoring that directory rewinds it. Database restoration rewinds all database audit rows. Independence across restores is not promised.

Writers serialize via a private directory lock, append and fsync one bounded line. A write/permission/lock failure emits a visible generic `Audit write gap` warning on stderr; app/commands continue and do not retry a successful action. Check directory ownership and disk availability. A writer crash can leave `.writer-lock`; after confirming no writer is active, the trusted operator may remove that empty lock directory. A crashed/killed run may have only a start, or no row if storage failed; that is incomplete evidence, never proof of success or automatic authorization to repeat a side effect. Concurrent runs have separate UUIDs. Database checksums and journal checksums detect accidental corruption cheaply; the machine owner can change or remove files and stays trusted. No backfill, collector or stdout-retention guarantee is added.

Tests use synthetic records, mocked providers and fake pg_dump/pg_restore/age/rclone. Local PostgreSQL verification uses an explicitly named throwaway compose project; never run maintenance scripts against production to verify auditing.
