# General audit trail

Settings > Audit trail and `python manage.py query_audit --member <app-member-id>` review the same authorized rows, ordered by newest UTC timestamp then event UUID, 50 per page. Use `--page`, `--action`, `--actor` (app member ID), `--source`, `--date-from` and `--date-to` (inclusive UTC dates). The command is read-only JSON, suitable for an offline reader; choosing a member does not grant a larger operator audience. Web responses use no-store. Do not save query output to public places.

This foundation records sharing, unsharing, changing sharing mode, archiving and permanent account deletion. It has no backfill and does not claim comprehensive action coverage. Correction history, sign-in/security records, import provenance and AI usage remain separate and are not copied. Later coverage must extend typed action/target enums and explicit append calls; request/download events must describe only what is known (for example export_generated does not prove delivery).

Each event contains a generated UUID and UTC time, enumerated action/outcome, trusted actor kind and nullable member/effective member references, target type and opaque app ID, audience references, source, UUID correlation/run ID, allow-listed changed field names and a SHA-256 checksum. There is no free-form payload, before/after values, actor name, amount, description, URL, raw row, credential or AI text. Correlation IDs must be UUIDs generated in trusted code, never arbitrary request headers. Sources and actors are supplied by trusted callers, never browser input. Use `append_event` inside the authorized action's database transaction, after the changed fields have actually changed. System callers supply their truthful scheduler/operator kind and the effective member whose access authorized the target.

For a surviving account, all its events follow current account authorization, including archived accounts. Only deletion events snapshot a private owner or household; earlier private history stays with an account that later becomes co-owned, and unshared history is not tied to a former household. The actor alone gains no access. Unsharing or membership exit revokes household access immediately, including counts and filters. On permanent account deletion, prior general events are removed; only metadata-only deletion events remain for the private owner or current members of the household at deletion. After member-data deletion, private events disappear and retained shared actor/effective-member references become null. If the household itself is deleted its audit audience goes too.

`AUDIT_RETENTION_DAYS` defaults to 90 and `AUDIT_PURGE_BATCH_SIZE` to 1000 (both positive). The daily background pass calls the bounded purge once; expired rows above its batch cap await subsequent daily passes. Retention and account/member/household deletion are the only application cleanup exceptions. No event edit/delete API, form or admin registration exists; the append-only model/queryset rejects ordinary saves, updates, bulk inserts and deletes. Database administrators and the machine owner remain trusted; this is not tamper-proof storage. Checksums cover immutable event metadata, excluding visibility and actor references deliberately changed by deletion/anonymization. The CLI reports checksum validity.

A normal action and its event commit/roll back together. If the audit insert alone fails, its nested transaction rolls back, the action continues, the UI displays a generic warning and the operator receives an ERROR-level "Audit write gap" log. Jobs/CLI report the same generic log. Warnings and gap reports run only after the enclosing action commits; a later action rollback discards them. Database error text and parameters are never included. The missing event cannot be recovered automatically; investigate the database and record the operational gap privately. Never retry an action that already succeeded just to obtain an event. Invalid metadata is a programming error, not this fallback.

The server clock supplies event times; UUID tie-breaking gives deterministic ordering, not causality or a guarantee against clock drift. Monitor the host clock. Committed rows survive restarts and are included in ordinary database dumps. Restoring an older dump rewinds the trail and removes later events, like other application data. There is no independent journal or retention across restores. Synthetic dump/restore and restart verification belongs on disposable test databases only.
