# Core financial data model

Updated: 2026-11-06. This document records the storage contract introduced by issue #4, the reimport rules from issue #6, correction history from issue #31, category/transfer/refund rules from issue #8, cash-flow reporting from issue #9, recurring-charge series from issue #17, household share modes from issue #30, SimpleFIN Bridge connections from issue #67, net worth from balance snapshots from issue #69, planned items with projected cash flow from issue #21, and split transactions from issue #97. Budgets come from issue #96. Notes and tags come from issue #98. Saved CSV mappings come from issue #101. Provider parsing and Vanguard-specific activity meaning remain separate issues.

## People and sharing

- `Person` is the financial-domain profile for one Django user.
- Privacy policy (issue #106): `PrivacyPolicyVersion` stores each published text, its version number, whether it is material, and the published time. `PrivacyPolicyAcceptance` is one row per member and version they accepted. A member is in acceptance when they have accepted the latest material version or any later version. `Person.privacy_policy_declined_version` records an explicit denial; `Person.privacy_policy_dismissed_version` separately records Not now. Both nullable FKs use SET_NULL. Migration #345 moves earlier Not now declines to dismissals. Only denial hides the sidebar AI slot; either response hides the policy bar for the latest material version. `household_consent_status` reports current members as accepted or not_answered (including denials), with batch acceptance lookup. `may_use_ai(member)` and `household_ai_allowed(household)` are the AI guards: the second is true only while every current membership of that household is in acceptance.
- AI provider layer (issue #91): `AiProviderConnection` is one encrypted Agent Harness App token per member and connection kind. The token uses the same Fernet key as SimpleFIN. `AiProviderConnection.offer_local_to_household` is off by default and only the connection owner can turn it on so other current household members may use that connection with backend `local` (#162). Hosted backends on that connection stay unusable by anyone else. `Person.use_shared_local_chat` and `Person.use_shared_local_background` are the requesting member's opt-in. Shared requests still run as that member (`visible_to`, policy, usage, jobs) and count toward a per-member daily cap. `AiJob` holds background work as feature name, member, input references, status, attempts, and a result reference — never copies of financial rows. `AiUsageEvent` records provider, backend, feature, token counts, and outcome, without prompts or responses. Tools and jobs always re-evaluate `visible_to` as the requesting member at run time.
- Bring-your-own API key (issue #147): `AiProviderConnection` kinds `anthropic_api` and `openai_api` hold a member's own provider key in `encrypted_token` (same Fernet key; `base_url` is empty). A member may hold one connection of each kind alongside the harness connection. `use_for_chat` and `use_for_background` mark which API connection answers each feature; choosing one clears the other choices for that feature (harness backend, shared local model, the other API key), and `resolve_ai` honors it when no backend is requested. The adapters (`finance/ai_api.py`) call Anthropic's Messages API and OpenAI's Responses API (`store: false`) through the redirect-refusing opener, run the same read-only chat tools, and are stateless: chat resends earlier turns, nothing is resumed. Models are allow-listed (Anthropic: claude-sonnet-5-5, claude-opus-5-5, claude-haiku-4-5-20251001, claude-fable-5-1; OpenAI: gpt-6.1-sol, gpt-6-astra, gpt-6-luna; chat defaults to the first, background to claude-haiku-4-5 or gpt-6-luna), checked against the providers' docs on 2026-10-05. Auth, rate-limit and quota errors map to `authorization_required` and `limit_reached` without repeating provider text. Usage events record tokens and outcome; settings shows an approximate monthly token count. Other members never use a member's API key.
- AI chat (issue #94): `AiConversation` is one tools-only Agent Harness session owned by the member who started it. It stores the harness session id bound to the connection that created it (`harness_connection` is that connection's id and `connected_at`, matching `AiJob` session resume), backend, title, turn and tool-call counts, the account, planned item, budget, savings goal and rule ids its tools quoted (goals and rules since #662, migration 0084), and an expiry (default 30 days). `AiConversationMessage` stores user, assistant, and error turns with cited figures (amount, currency, page URL) and optional page context of route plus query parameters only. Conversations are listed only to that member, can be deleted one or all, expire automatically, go into that member's export, and are deleted when their member can no longer see an account, planned item, budget, savings goal or rule they quoted: the row is deleted, unshared or made private (#451, #569), or the member leaves the household. Conversations stored before those ids were recorded are treated as having quoted every planned item and budget their member could have seen while they were open (migration 0076), so they fail closed. The model reaches data only through read-only tools that call the same `visible_to` services as the pages. Transaction rows from `list_transactions`, `search_transactions`, `transfer_suggestions` and `category_suggestions` carry `category` (the list's label, with a household name withheld before consent), `tags` (names withheld before consent) and `note` (first 500 characters, `note_truncated` when cut) through `TransactionLabels` (#684). `AiConversationMessage.charts` (#646, migration 0080) holds the charts the `make_chart` tool drew for a reply: the validated request (kind, report, dates, filters) and the series the server computed from the report page's own service, with the page link. The model names only a kind, report, dates and filters from an allow-list; any other argument is refused, so it never supplies a value. Charts follow the tools' account and household-consent scope (their report links carry `scope=private` while consent is incomplete, and budget and net worth charts wait for consent because those pages have no private-only view), record the accounts and budgets they used like any tool, are capped at 24 periods, 12 categories (the rest summed as "Other") and 3 per reply, live only in the reply, and are deleted with the conversation.
- Chat lookups (issue #662, migration 0084): read-only tools in `finance/ai_lookup_tools.py` answer from savings goals (`goal_progress` plus the Savings plan's funding month), the debt planner, Home's what-if scenarios (changes are built into the page's own `sc` tokens and checked against the member's projection inputs, so an amount or pause change only reaches a planned item or series that projection holds; nothing is saved), categorization rules, and one active account's balance snapshots with source and note (an archived account has no Balances page to cite, so the tool refuses it and points to Net worth's month ends). They follow the other tools' account and household-consent scope: while consent is incomplete, household goals and rules stay out, a private goal linked to a shared account withholds its progress, a private rule's shared account and household category name are masked, and funding months are withheld when a household safety buffer or a shared balance behind any goal would shape them. Each reply records the goals and rules it quoted (`used_goal_ids`, `used_rule_ids`, migration 0084, owner decision 2026-11-05): leaving the household, a household goal made private, and a rule deleted with the account it names purge the conversation through `delete_conversations_without_access`, and any other loss of a quoted row purges it at the next reply, as for the other quoted rows. A household rule cannot be made personal (only a rule's own owner may set it personal), so that edit needs no purge. Unsharing an account a conversation never quoted leaves it alone. A reply that quotes funding months records every account and planned item the Savings plan's projection read, and a debt plan records every in-scope debt it simulated.
- Chat attachments (issue #644, migration 0081): `AiChatAttachment` belongs to one conversation (and the question it was sent with) and cascades with it. It stores the uploaded bytes, the text parsed once at upload (`content`: sheet rows with their row numbers, or PDF page text), a `summary` of sheet names and row and column counts or the page count, the sniffed kind (`csv`, `xlsx` or `pdf`), the size, the display name, and the provider named in the upload warning (`provider`: chat backend plus the connection marker of row id and `connected_at`, since two connections can share a backend name and a reconnect, even to another server, keeps its row). Nothing is written to disk. Its `visible_to` follows `AiConversation.visible_to`. The `read_attachment` tool is bound to the conversation and provider when a turn starts and refuses files from other conversations or other members. `AiConversation.attachment_providers` records the providers the chat has warned will receive the conversation's files: the one named at upload, and each later one whose switch warning the member saw before asking (owner decision 5). Only those read the files or are resent earlier turns; the list is kept after a file is removed. A long row or PDF page is read in parts (`column`, `char_offset`). Attachments are not part of the data export.
- AI category suggestions (issue #93): `CategorySuggestion` stores one pending, accepted, or rejected suggestion per member and transaction. It records the suggested category, provider, backend, and a snapshot hash of the transaction fields the suggestion was based on. A stored row expires when that snapshot no longer matches. Suggestions are queued as `category_suggestions` jobs after import commit and SimpleFIN sync, and from the Uncategorized filter, only for rows still uncategorized after rules. Accepting calls `assign_category`; a suggestion never overwrites a hand-set or rule-set category and never changes transfers or pairing.
- Chat cleanup cards (issue #661, migration 0085): `AiProposal` kinds `recurring`, `transfers`, `ai_suggestions`, `notes` and `splits` use the checkbox item card from #659. Read-only chat tools list open recurring suggestions, suggested transfer pairs and pending AI category suggestions inside the AI account scope (#521: a series or pair touching a household account stays out until household consent, and a household category name is withheld). Each stored row keeps a snapshot of its target: a series' status and fingerprint, a pair's status, a row's untracked mark, a suggestion's status, snapshot hash and category, a hash of the current note (never the note itself), or a transaction's amount and category. Apply re-reads the row as the member, marks it stale when the snapshot moved ("Already confirmed."), and calls the manual service: `confirm_recurring_series`/`dismiss_recurring_series`, `confirm_transfer_pair`/`dismiss_transfer_pair`, `mark_untracked_transfer`/`unmark_untracked_transfer`, `accept_suggestion`/`reject_suggestion`, bulk edit's append-note step (a note line below the current note, with a correction-history row and, as on every note path, no audit event), and `split_transaction`. Split parts are positive cents that take the transaction's sign and must add up exactly; a split, transfer, linked refund or purchase with a visible linked refund is refused at propose time and edited on its own page.
- Chat balance cards (issue #660, migration 0086): `AiProposal` kind `balances` uses the checkbox item card from #659 for manual balances, for example month ends read from an attached statement. Each row names an active account inside the AI account scope (#521), a date, an amount in cents in the manual sign (a credit card or loan stores the amount owed as a positive number, which the card says in plain words, while `balance_history` reports owed amounts as negative), an optional net contribution (investment accounts only) and an optional note. Rows are checked with the Balances page's own `ManualBalanceForm` and refused one by one with the reason: an account outside the scope (answered like a missing one), an archived account, a future or pre-1900 date, a date SimpleFIN already reported (a synced balance outranks a manual one on the same day, so a manual one would change nothing), a second row for the same account and date, or a row identical to the manual balance already there. A manual balance already on that date is kept as the row's snapshot (id, amount, net contribution and a hash of its note, never the note itself) and shown before → after; an omitted note or net contribution keeps the existing one. Apply re-reads the account as the member, locks it and that date's manual row, marks the row stale when the account's type, the manual row or a new SimpleFIN balance moved, and records through `record_manual_snapshot` (audited as `record_created` or `record_edited` on the balance, with the chat source and proposal id).
- `Household` groups people through dated `Membership` rows. A database constraint allows at most one membership without an end date for each person. Ended rows remain as history.
- Deleting a member's data (issue #104): private accounts are removed through the account-deletion path. Personal rules, private budgets, private planned items and savings goals, recurring series, AI and SimpleFIN rows, policy acceptances, recovery codes, the Google link, and sessions are removed. Shared household rows stay. Actor references on remaining history (`TransactionCorrectionHistory`, `ImportBatch.imported_by`, `RuleApplication.applied_by`, `Invitation.invited_by`, `BudgetRolloverReset.actor`, and ended `Membership.person`) are set null and display as `former member`. A current membership cannot have a null person. Lent household accounts must be handed over (converted to co-owned, then ownership follows the leave rules) or deleted with the member. If the member was the last current member, the household, its categories, and its other household-scoped rows are removed after those accounts become private and are deleted.
- Every `Account` always has one owner. Its scope is either `private`, with no household and an empty share mode, or `household`, with exactly one household and a share mode of `co_owned` or `lent`. A database constraint rejects any other combination. Transactions and import batches inherit their visibility from their account instead of copying a scope that could drift. `Account.objects.visible_to` still follows current household membership, so a lent account that reverts to private is immediately invisible to other members.
- Share modes (issue #30): co-owned accounts belong to the household; any current member may unshare or archive them, and if the owner leaves, ownership moves to the longest-standing remaining member (or the last member takes them private). Lent accounts stay owned by the lender; other members may view and edit transactions while they belong to the household, but only the owner may unshare, archive, or change the mode. If that owner leaves, the account becomes private to them and history is preserved. Existing household rows migrate as co-owned.
- Account ownership and membership use protected foreign keys. The lifecycle actions in issue #3 must transfer ownership or change scope before removing related records. Issue #3 also owns access-filtered query APIs and authorization enforcement.
- Accounts, transactions, and import batches use `active` or `archived` status. Archiving requires an archive timestamp and preserves provenance and transaction history.

## Money and transaction meaning

- `Transaction.amount_minor` is an exact signed 64-bit integer. Negative means money out and positive means money in for every account type, including credit cards. Balances have separate future semantics.
- Every account and transaction stores its currency explicitly. V1 accepts only `USD`; database constraints reject another currency.
- V1 account types are `checking`, `savings`, `credit_card`, `investment`, `real_estate`, `vehicle`, `precious_metals`, `other_asset`, and `loan`. Physical asset and loan accounts have no cash-flow transactions. A loan may optionally name a `secured_asset` of the same scope (both household, or both private to the same owner).
- Ordinary imported rows have kind `cash_flow`. Unverified Vanguard activity has the neutral `investment_activity` kind and retains its opaque source fields. It must not affect income or spending reports until issues #15 and #9 define verified treatment. The schema intentionally has no invented symbol, quantity, or price fields.

## Import provenance

- An `ImportBatch` identifies its account, importing person, source provider, user-selected date range, import timestamp, SHA-256 hash of the discarded source file, and optional `saved_csv_mapping` when a household saved mapping was applied. The application must discard uploaded CSV contents after a successful import.
- Saved CSV mappings (issue #101): `SavedCsvMapping` is household-wide. It stores a unique active name per household, the mapped file's header list (never cell values), the generic mapper's parsing fields, the creator, timestamps, and `locked_at`. Any current household member may use and manage them; former members cannot. After a batch is committed with a mapping, parsing fields lock; only the name and per-account default remain editable. A mapping that has imported a batch is archived rather than deleted. `Account.default_saved_csv_mapping` pre-selects that mapping on the account's import page. Reuse applies the stored mapping only when the uploaded headers match the stored headers exactly, in the same order; otherwise the generic mapper is shown and the app does not guess.
- Each transaction identifies its batch, source row number, optional provider transaction ID, and a SHA-256 fingerprint of account id, ISO date, signed minor amount, and the stored description (newline-separated). The fingerprint is computed at import and never rewritten. It is not unique: the same fingerprint may occur more than once on an account when the export contains legitimate repeated purchases. Overlap detection counts active fingerprints on the target account only (the account the importer can already see); archived rows do not count, so an undone batch can be reimported. A matching fingerprint on a different account is not an overlap. The Huntington checking profile stores `Transaction Number` as `source_transaction_id` and does not use it for overlap matching.
- Reimport preview reports new, duplicate, and invalid counts. Commit creates an import batch only when at least one row is new, stores those rows with batch provenance and original field names/values, and discards the staged CSV. Duplicate valid rows are left on their original batches. Undo archives one active batch and only that batch's transactions.
- `original_fields` is a JSON object on each transaction. It keeps the imported row's original field names and values without retaining a batch-level raw file. These values are financial data: never write them to logs, errors, fixtures, issues, or screenshots.
- Deleting related people, accounts, or batches is protected at the database relationship level. Correction and undo features must archive records rather than hard-delete them.

The committed `synthetic_demo` fixture contains invented names, hashes, descriptions, and amounts only. It is suitable for schema demonstrations, not provider-format verification.

## Transaction review and correction

- The transaction review UI starts with `Transaction.objects.visible_to(person)` on every request, excludes archived transactions, and orders by transaction date and then primary key descending.
- User corrections may change `transaction_date`, `description`, and `amount_minor`. Category assignment, transfer exclusions, and refund links are separate writes from issue #8 and also append correction history. Amount entry converts decimal major units directly to integer minor units without using binary floating point.
- Each changed field writes one append-only `TransactionCorrectionHistory` row in the same database transaction as the correction (lock order: memberships, then account, then transaction, then history insert). A no-op save writes none. Amounts on history rows are integer minor units plus currency. History is listed through `TransactionCorrectionHistory.objects.visible_to`, which is `Transaction.objects.visible_to` on the parent row, including shared and archived accounts. Transfer exclusion entries are listed only when the viewer can see both legs of every pair the transaction belongs to. History values are never written to logs or error messages.
- Corrections never replace `original_fields` or change the transaction's account, import batch, source row number, fingerprint, currency, or kind. Those fields continue to describe the imported record and its provenance.
- The list shows the assigned household category, `Uncategorized` when none is assigned, `Transfer (untracked account)` when the row is marked as a transfer to or from an untracked account (#642), `Transfer` when both legs of an exclusion pair are visible to the viewer and still active, and `Split (n)` with each part when `category_source` is `split`. It also shows household tag badges and a truncated note, with the full note available on the list.
- Notes and tags (issue #98): `Transaction.note` is free text up to 2,000 characters, blank by default, and follows the transaction's visibility. Editing a note is not recorded in correction history. `Tag` is household-scoped with a case-insensitive unique name, an archived flag, and timestamps. Archived tags stay on transactions but cannot be newly applied. `TransactionTag` links a transaction to a tag, unique together, and cascades when the transaction is deleted. A reimport never changes notes or tags. Account deletion removes the account's transaction notes and tag links.
- Rule and recurring notes (issue #684, migration 0087): `CategoryRule.note` and `RecurringSeries.note` are one-line text up to 2,000 characters, blank by default; `RecurringSeries.note_updated_at` is when the series note was last set. `finance/auto_notes.py` appends the line below a transaction's note unless that exact line is already one of its lines or the result would pass 2,000 characters, in batched writes, and writes a `note` correction-history row whose new value ends in ` (rule: <contains text>)` or ` (recurring: <series name>)` (notes still write no audit event). Rules add it only in `apply_enabled_rules_to_transactions` (new imported, synced and manual rows the rule wins), never in `apply_rule`. A confirmed series adds it where members are created (detection in `_apply_detection`, `add_recurring_members`, `merge_recurring_series`) to charges with `created_at >= note_updated_at`, so an older charge absorbed later is left alone. A merge target without a note takes the source's. Existing rows get the line only through `apply_rule_note_to_existing` / `apply_recurring_note_to_existing` (a rule's rows are its current matches plus, for an untracked-transfer rule, the rows already marked, which `_candidate_base(keep_marked=True)` keeps): the page posts a sha256 of the previewed row ids (`preview_token`, one field however many rows) and the version (the rule's `updated_at`, the series' `note_updated_at`), the service re-reads them under lock, refuses if either moved, and stores a `BulkEditUndo` snapshot in bulk edit's `append_note` shape so `undo_bulk_edit` restores the previous notes. A note-only rule edit keeps `confirmed_at`. Only the series owner (`visible_to`, confirmed) may set or apply its note. The export writes `note` and `note_updated_at` on `recurring_series` and a `category_rules` file of the member's visible rules with their notes.

## Categories, transfers, and refunds

- Each household has an editable category list seeded with Income, Groceries, Dining, Transportation, Housing, Utilities, Health, Insurance, Shopping, Entertainment, Subscriptions, Travel, Education, Personal care, Gifts and donations, Fees and interest, Taxes, Uncategorized, and the system Transfer category. Transfer cannot be assigned by hand and is never itself what excludes a row from income and spending.
- `Transaction.category` is optional. Clearing it leaves the transaction uncategorized.
- A `TransferPair` records two transactions (`leg_a_id` < `leg_b_id`), a confidence reading (`high` or `low`), a list of reasons, a kind (`transfer` or `card_payment`), and a status. High confidence means each leg has exactly one counterpart in the configured date window, the direction is plausible, and at least one leg's description carries payment or transfer wording (see below); only high-confidence pairs are auto-marked, and every other candidate stays a low-confidence suggestion until confirmed. Auto-marked and confirmed pairs are excluded from income and spending only when both legs are visible to the person asking and both remain active. Archiving, unsharing, or undoing an import of an account or batch revalidates every pair with a leg there even when the other leg is not visible to the actor, unmarks pairs that no longer hold, and restores snapshot categories on surviving legs. The same viewer rule applies per row: the list label, the edit page's Split and Link-a-refund sections, the split service, bulk edit and chat proposal cards all read transfer state from `exclusion_exists_for(viewer)`, and `Transaction.is_excluded_transfer` refuses to answer without that annotation rather than consulting pairs the viewer cannot see (issue #299). Suggested pairs are not excluded until confirmed. Suggestions whose legs no longer cancel are invalidated so they stop occupying those transactions, and pairing then recomputes. Undoing restores the category ids stored at mark time. Dismissed and undone pairs are not auto-marked again.
- Untracked transfers (#642): `Transaction.untracked_transfer` (boolean, default false) marks a cash-flow row as money moved to or from an account the planner doesn't track. The mark is on the row, so it applies to every viewer of the row. `exclusion_exists_for(viewer)` is `untracked_transfer OR` the viewer-scoped pair rule above (in both its default and `household_only` forms), and `excluded_transfer_ids(viewer)` is the set of visible row ids that expression selects, so every report, the edit page, bulk edit, the filtered CSV and the data export read one rule; a row that is both marked and a pair leg is still one row and is left out once. Undoing, dismissing or revalidating a pair never touches the mark, and marking never touches the row's category or any pair. `finance/untracked_transfers.py` sets and clears it: the row is locked with `_lock_accounts_and_transactions` (visible means editable), investment-activity rows and investment accounts are refused (the check constraint `transaction_untracked_not_investment` backs the first), a linked refund is refused, and a row already left out by a pair is not marked again. Each change writes one `TransactionCorrectionHistory` row with `field_name="untracked"` ("Counted in income and spending" ↔ "Transfer (untracked account)", with " (rule: …)" when a rule marked it), listed through the ordinary `visible_to` (not the pair-hidden `exclusion` field), and a `transaction_corrected` audit event with changed field `untracked_transfer` unless the caller's origin is bounded (bulk edit and rule runs write one event per account or rule). Marking a purchase calls `drop_refund_links_to_originals`, as archiving does (#570); unmarking does not restore those links. Bulk edit has `mark_untracked` and `unmark_untracked` actions whose undo snapshot stores the previous flag. The data export's transactions table has an `untracked_transfer` column.
- Auto-mark evidence (issue #294): equal amounts are not enough. A pair involving a credit card must be a bank-side debit with a card-side credit; a bank-side credit with a card-side debit is never auto-marked. At least one leg's description must contain a whole-word, case-insensitive term from `PAYMENT_VOCABULARY` in `finance/pairing_evidence.py` (payment, pmt, pymt, autopay, epay, e-payment, transfer, xfer, ach, online banking, crcardpmt; payment and transfer also match plurals). Wording on either leg is enough, so an issuer that labels its payment credit generically still pairs through the bank-side wording. Without both, the pair stays `suggested` and its `reasons` say which check failed. Revalidation downgrades an `auto_marked` pair that no longer meets the rule (for example after a description edit) to `suggested`, restoring snapshot categories. Migration 0060 applied the rule once to existing auto-marked pairs and logged only counts; confirmed, dismissed and undone pairs were left alone.
- Pairing requires opposite signs, equal absolute amounts, different accounts, dates within the household match window (default 5 days), and at least one person who can see both accounts. Detection runs on the actor's visible transactions only. Saving a new match window revalidates suggested and auto-marked pairs, undoes auto-marked pairs that no longer fit the window (restoring snapshot categories), leaves confirmed pairs, and then refreshes pairing. When one member's action refreshes pairing for every member (saving the window, splitting or unsplitting), new pairs are detected only among rows that member can also see; each member's own refresh covers pairs involving their private accounts.
- A `RefundLink` is a manual link from a refund transaction to an original. The refund must be a positive amount and the original a negative purchase of the same transaction kind; otherwise the link is rejected with a safe message. The refund stores the inherited category on itself. Recategorizing the original copies that category onto linked refunds and records correction history, but only onto a refund that every member who sees it can also see the original of, and that the acting member can see (issue #567). In practice the refund is on a private account of a person who sees the original, or both sit in household accounts of the same household. Every copy path (assign, split, unsplit, split-part recategorization, bulk edit and its undo, rule apply and reverse, transfer-pair unmark) goes through `refunds_following_originals`. Unmarking a pair copies from the linked part when the original is split, not from the split original's empty category, changes nothing when the refund already has that category, and leaves a split leg's own category empty rather than restoring its snapshot. A category change an unmark makes on a row that a member who cannot see both legs also sees, now or after joining, gets no audit event and is recorded only `only_for` each viewer of that row who sees both legs, so nothing reveals the pair to the others. The audit event for confirming, dismissing or undoing a pair is recorded on a leg whose viewers, now and after any member joins, all see the other leg, for the same reason (#580). Any other linked refund, such as a household refund whose original was since unshared, a former member's private refund, or another member's private refund, keeps its category and gets no correction history; the link still counts toward spending as before. `income_and_spending_totals` never treats a linked refund as income; it subtracts the refund's own amount from spending in the refund's stored category without requiring the original to remain visible and without exposing the original. A link lasts only while its original counts (#570). When the original is archived (undone import, deleted manual entry, archived account), `drop_refund_links_to_originals` deletes its links, locked in pk order, and writes "linked" -> "unlinked" `refund_link` history on each refund, whoever can see it. When the original becomes a confirmed or auto-marked transfer or card-payment leg (`_snapshot_and_mark`), `drop_refund_links_for_pair` applies the pair's viewer rule: it deletes a link the same way only when every viewer of the refund, now and after any member joins, sees both legs (a private refund whose owner sees them, or a household refund whose legs are both in that household). Otherwise a `RefundLinkDrop` (link, person, pair) records each current viewer of the refund who sees both legs. The link then no longer counts in that person's own totals, and `RefundLink.objects.visible_to` and the data export omit it for them. Their "linked" -> "unlinked" history row has `TransactionCorrectionHistory.only_for` set to them, so `TransactionCorrectionHistory.objects.visible_to` lists it to no one else, even after the link is later deleted; no audit event is written. Household-scope totals ignore drops, as they ignore pairs with a private leg. `link_refund` applies the same rule to a new link whose original is already a marked leg for another viewer. `share_account` and `change_account_share_mode` apply it again through `reapply_refund_link_drops_for_account`, for marked pairs with a leg in that account, so a member who newly sees both legs does not keep a link whose original no longer counts for them (#579). They lock the pair's other account and the refunds' accounts first, in pk order. `unshare_account` and leaving never apply it, and existing `RefundLinkDrop` rows stay as they are. The refund keeps its category and counts as income for whoever the link was dropped for. While the link stands for another member, a member it was dropped for cannot relink the refund: `link_refund` raises `REFUND_LINK_STANDS` (a validation error, not a permission error) and the refund page shows that note in place of the link form (owner decision 2026-10-23, option c). Only a deleted link can be relinked by hand. Every path that unmarks the pair (`_unmark_exclusion` and the leg-less fallbacks in revalidation and account delete) calls `restore_refund_links_for_pair`, which deletes that pair's drops under the same `RefundLink` row locks; a member with no drop left gets an "unlinked" -> "linked" row `only_for` them, so the link counts again for them. A deleted link is not restored. `_totals_base` reads drops through one per-viewer `NOT IN` subquery, and household-scope totals ignore them. Reversing migration 0077 deletes every `only_for` history row rather than let 0076 list it to all viewers.
- Split transactions (issue #97): `TransactionSplit` stores one part of a split cash-flow row: household category, signed `amount_minor` (same sign as the parent, never zero), and position. A split has at least two parts that sum exactly to the parent. While split, `Transaction.category` is empty and `category_source` is `split`. `RefundLink.original_part` is required when the original is split; that refund inherits the part's category. Cash-flow income and spending still use the whole transaction; spending-by-category attributes each part (and a refund linked to that part) to the part's category. The Split form lists, and asks a part for, only refunds the actor can see (`RefundLink.objects.visible_to` / `Transaction.objects.visible_to`). Linked refunds the actor cannot see (for example another member's private-account refund) are never listed, counted, or mentioned; their link is assigned automatically to the largest part (ties: the first part by position), but their category is left alone, as for any refund the actor cannot see (#567). A listed refund takes its part's category only under the same rule as recategorizing, as it does when a part is recategorized or the purchase is unsplit (the unsplit clears every link's part either way).
- Rule actions (#642): `CategoryRule.action` is `categorize` (default; `category` required, `scope_household` empty) or `untracked_transfer` (`category` empty, `scope_household` set to the saving member's household), enforced by `category_rule_action_target`. A categorize rule takes the household its personal-rule matches must belong to from its category; an untracked-transfer rule has no category, so `CategoryRule.rule_household_id` (and the `Coalesce` used inside rule queries) reads `scope_household` instead, and a personal one goes inactive the same way after its owner leaves that household. An untracked-transfer rule's candidates are active cash-flow rows outside investment accounts that are not linked refunds and not already left out (`_candidate_queryset(untracked=True)`); unlike a category rule it also reaches hand-set and split categories, because it keeps them. Applying writes `RuleApplicationEntry.marked_untracked=True` with the row's unchanged category snapshot; reversing such an entry clears the mark only while it is still the one that application made (no `untracked` history on the row after `applied_at`), so a mark a member removed and set again stays. Reversal treats category entries and mark entries separately: a later entry supersedes an earlier one only when it changed the same thing, and the category chain in `_category_before` skips mark entries. Import and sync auto-apply checks each row's winning confirmed rule against the candidate set for that rule's action. Migration 0079 adds the columns with defaults that leave every existing row, pair and rule as it was; reversing it deletes untracked-transfer rules with their applications and the `untracked` history rows.

## Recurring charges

- Detection is a local deterministic function over `Transaction.objects.visible_to` for the viewer. It never includes investment activity, positive amounts, or rows excluded by a visible transfer/card-payment pair (#8 helpers).
- A `RecurringSeries` belongs to one person and has an `is_active` flag. Visibility is that person plus a check that every member transaction is still `visible_to` them, so a private account cannot leak through another household member's suggestions, totals, or errors.
- Series identity for dismiss is a SHA-256 fingerprint of the sorted member transaction ids. A dismissed fingerprint is not suggested again until that set of transactions changes. Confirmed series stay confirmed and absorb later occurrences of the same merchant, cadence, and amount band (within 25% of that series' typical amount). One confirmed row is never reassigned onto a second amount cluster, and a refresh never writes a fingerprint that already belongs to another series for that person. Refresh keeps a confirmed series active while at least one of its member occurrences is still eligible, even if those leftovers cannot form a detected chain; it marks the series inactive and clears members only when none remain. A later eligible chain of the same merchant, cadence, and amount band can reactivate it; inactive confirmed series are omitted from Recurring-page totals.
- Cadences are weekly, biweekly, monthly, quarterly, and annual, each with a few days of calendar tolerance. Two occurrences are stored as `possible`; three or more at a regular interval are `suggested` until confirmed. The 25% amount band is rolling: each charge is compared with the median of the up to two accepted charges before it, and a confirmed price change (the next charge agrees with the new price and is outside the old level) resets that level. Exact amounts raise confidence above varying amounts. When a picked chain fails that band, detection drops the charge that breaks the rolling band by the most and re-picks before falling back to amount clusters.
- Typical amount is the median of the latest three member occurrences (or all of them if fewer), stored as a negative minor-unit integer. Monthly and annual equivalents derive from it (annual is typical absolute amount times occurrences per year; monthly is that annual figure integer-divided by 12). The Recurring page lists confirmed series and those totals; suggestions on the same page can be confirmed or dismissed. Members may merge series, remove a charge (recording a `RecurringExclusion`), or add an eligible charge. `RecurringSeriesMember.source` is `detected` or `manual`; refresh keeps manual members and never creates a second series that overlaps an existing active one.
- Recurring review (#102): `cancelled_at` is set when a member marks a confirmed series cancelled. Cancelled series keep members and history but are omitted from monthly and annual totals and from the cash-flow projection. A matching member charge dated after `cancelled_at` is shown as resumed until the member confirms (clears `cancelled_at`) or keeps the series cancelled (those later charges become `RecurringExclusion` rows). `RecurringPriceAcknowledgement` (one row per member and series, unique) stores the latest charge amount that member dismissed as a price-change flag, and the dismissed charge itself (`transaction`, null for dismissals migrated from before it was recorded); the flag returns for that member only when the latest amount differs from that value and still drifts past their threshold from the usual price. Dismissals are per member (#523): dismissing a household bill's flag writes a row for every copy of the bill the member may act on and leaves other members' flags and alerts alone. The member's export keeps the `acknowledged_amount_minor` column on their own series, filled from their own dismissal. Household bills raise review alerts once per bill per recipient (#523): the daily pass groups members' copies with `bill_grouping` and keys the price alert on the first charge of the latest run at the new amount (`recurring:bill:<charge id>:<amount>`) and the missed alert on the bill's latest charge (`recurring:bill:<charge id>:missed:<date>`); a recipient already alerted under a copy's earlier per-series key is not alerted again. Other series keep `recurring:<series id>:…` keys. Price drift (#418) compares the latest charge with the usual price, the median of up to 12 charges before it (the latest is excluded; an even count averages the two middle values). Fewer than 2 prior charges or a zero median means no baseline. `AlertSettings.recurring_price_percent` (integer 1-100, default 10, database check constraint) is each member's threshold: a charge flags when `abs(latest - median) / median` is strictly greater than that percent, so a drift of exactly the threshold does not flag. Household series evaluate the threshold per alert recipient, and the recurring review page uses the viewer's. `confirmed_at` is set when a member confirms a series, or when a merge first makes it confirmed, so a monthly review can list series confirmed in that closed month.

## Planned items and projected cash flow

- `PlannedItem` belongs to an owner and is either `private` (no household) or `household` (exactly one household). Current household members can see and edit household items. Private items are visible only to their owner.
- Amounts are stored as a positive minor-unit integer in USD. Income versus expense comes from `kind`. Cadence is one-time, weekly, biweekly, monthly, quarterly, or annual. An optional end date must fall on or after the start date. An optional `replaces_series` link skips that confirmed recurring series in the projection.
- The projection engine is a pure month-by-month function. It starts the month after `today`, runs for 3, 6, 12, or 24 months (default 12), and counts discrete occurrences in each calendar month. Confirmed, active recurring series that remain `visible_to` the viewer are expenses at typical amount and cadence, starting after the latest member transaction date. Disabled items, another member's private items, and private-account series the viewer cannot see are omitted.
- Projected months are appended to the cash-flow chart and table with a Projected label. They are not added into actual summary cards, exports, or historical reports.

## Savings goals and the funding plan (issue #295)

- `SavingsGoal` (private to its owner, or household-shared) keeps its name, `target_amount_minor` (positive USD minor units), optional linked account and manual amount. A linked account's current amount is its latest snapshot through net worth's `signed_balance_minor` (issue #571), so a credit card or loan counts the amount owed as negative and never as money saved. `target_date` is optional. `priority` is a nullable integer of at least 1 (1 is funded first). `time_sensitive` is a boolean, default false. `depends_on` is a nullable self-reference (`SET_NULL`, related name `dependents`); a database check stops a goal depending on itself, and the services reject loops and links across scopes.
- `Household.savings_buffer_minor` is nullable. Null means the default buffer (one month of average actual spending over the last 3 complete months); 0 means no buffer; the value cannot be negative.
- Funding plan calculation, in order: (1) open goals (active, not completed) in the chosen scope; (2) fill order by priority (null last), then eligible-after-dependency, then id, where a dependency that is completed, archived or outside the plan no longer holds a goal back; (3) the surplus for each projected month is `income_minor - spending_minor` from the existing projection; (4) while the buffer is unmet, a positive surplus tops it up first; a negative surplus changes nothing; (5) the rest fills the first unfunded goal up to its remaining amount (`target - current`, never below 0) and any leftover continues to the next goal in the same month. The first month a goal reaches zero remaining is its funded month. Nothing is stored; the plan is recomputed on each view.
- The wishlist import adds no table. A staged upload lives in the existing import staging directory and is deleted on commit, cancel or expiry. Each created or changed goal records the usual goal audit event; an unchanged goal records none.

## Budgets

- `Budget` is private (owner only, no household) or household (exactly one household). Current members can see and edit household budgets. Private budgets are owner-only; a former member loses household budget access immediately.
- Optional `category` is a household category; null means the overall monthly spending total. One active budget per private owner and category (or total), and one active budget per household and category (or total).
- `BudgetAmount` stores `effective_month` (first of a month) and `amount_minor` in USD. The amount for month M is the latest `effective_month` on or before M.
- Optional rollover starts the month it is turned on. `BudgetRolloverReset` records a month, actor, and time; carry from that month is zero. Carry is `amount − spent` summed from the later of the rollover start and the last reset through the prior month, and may be negative.
- Spent amounts come from `spending_by_category_report` for the month and scope so they match the Spending page.

## Cash flow over time

- Period totals call `income_and_spending_totals` for each window so transfer (pairs and untracked-transfer marks, #642), refund, and investment rules are not re-derived. Optional account lists are intersected with `Account.objects.visible_to`.
- Missing-import flags use active `ImportBatch` date ranges on those same visible selected accounts. A period is flagged when any selected account has no overlapping active batch; the flag is separate from the zero amounts.
- Unverified `investment_activity` rows remain omitted from income and spending; the home view states that when an investment account is included in the selection.

## SimpleFIN Bridge (verified from https://www.simplefin.org/protocol.html, 2026-10-01)

Facts below are from the published protocol. They are not inferred from a live bank export.

**Claim.** The setup token the member pastes is Base64 of a claim URL. The app POSTs to that URL once and stores the Access URL from a 200 response. The Access URL includes HTTP Basic credentials. Only `https` claim and access URLs are used. A 403 on claim means the token does not exist or was already claimed and may indicate compromise; the UI says so without echoing the token or URL.

**Fetch.** Account data is `GET {access_url}/accounts` with optional `start-date` and `end-date` (Unix epoch; start inclusive, end exclusive). `pending=1` would include pending transactions; the default omits them. `balances-only=1` omits transaction arrays. `version=2` selects this protocol version. A 403 on `/accounts` means authentication failed or access was revoked. A 402 means payment is required.

**Account Set.** `errlist` is the structured error list (required in v2). `errors` is a deprecated array of display strings. `connections` and `accounts` are required. Each Error has `code`, `msg` (user-facing), and optional `conn_id` / `account_id`. Prefixes are `gen`, `con`, and `act`. Unknown subcodes fall back to the prefix. `msg` values are sanitized before display and never logged with access URLs.

**Account.** `id` is unique within a Connection (not globally). `name` is the account label. `conn_id` ties it to a Connection. `currency` is an ISO 4217 code, or a URL for a custom currency (points, miles). This app stores USD only. An ISO 4217 code other than `USD` is converted at the ECB rate (see **Foreign-currency accounts** below); a URL or other value that is not a three-letter code is skipped for that account. `balance` and optional `available-balance` are numeric strings as of `balance-date` (Unix epoch). The protocol Account object has no account-type field; institution comes from the matching Connection `name`. The member chooses the app account type when linking or creating. Physical asset types are not SimpleFIN-linked; loans use `balances_only` like investments.

**Transaction.** `id` is unique within that SimpleFIN account. `posted` is a Unix epoch; it may be `0` when pending. `amount` is a numeric string: **positive means money deposited into the account** (same sign as this app). `description` is required. Optional `pending` is true when not yet posted (default false/absent). This app imports only posted transactions (`pending` not true and `posted` not 0), using the local calendar date of `posted` as `transaction_date`, and stores `id` in `source_transaction_id`.

**Foreign-currency accounts (#441).** A linked account whose currency is an ISO 4217 code other than `USD` is converted to USD instead of blocking its connection. `finance/fx_rates.py` asks Frankfurter (ECB reference rates, no key) for one date range per currency, `GET https://api.frankfurter.dev/v1/<start>..<end>?base=<CUR>&symbols=USD`, through the same address-vetted, redirect-refusing `simplefin_client.urlopen` with a 10-second read timeout, a 20-second deadline and a 512 KB response cap. The lookup runs before the database transaction and household lock, like the SimpleFIN fetch. Each transaction uses the rate for its own posted date, and a balance snapshot the rate for its snapshot date; a weekend or holiday takes the latest earlier business day within 7 days, and the rate's actual date is kept. The amount is `original * rate`, rounded half-even to the cent once. The transaction stores USD in `amount_minor` and `currency`, and `original_fields` keeps the provider's `amount` in its own currency plus `fx` (`currency`, `rate`, `rate_date`). `BalanceSnapshot` has `original_amount`, `original_currency`, `fx_rate` and `fx_rate_date`, all empty for a USD balance (a check constraint keeps them all-or-nothing). Rows already imported are never re-converted. If no rate can be had (network error, bad response, no rate within 7 days) or the account reports an unusable currency (a custom-currency URL or a malformed code), only that account is skipped for the sync: its work rolls back in its own savepoint, the other accounts on the connection sync, the connection does not fail, and the connection page's last-sync line names the skipped account. The next sync retries. Reconciliation leaves out an account that has a converted snapshot, because a balance change and the sum of rows converted at different dates differ by exchange-rate movement. A missing or blank currency is taken as USD and syncs without a rate lookup (owner decision, #627): SimpleFIN sends `""` for Vanguard accounts, and the connection page's link table shows "Not provided by SimpleFIN; treated as USD" for them. Full multi-currency support (reports, budgets, display currency) is a later item.

**Storage.** `SimpleFinConnection` belongs to one `Person`. The Access URL is Fernet-encrypted (`FIELD_ENCRYPTION_KEY`) and is never rendered, logged, or placed in errors. `AccountLink` maps one app `Account` to one SimpleFIN account id on that connection, with a cut-over date and mode `transactions` (checking, savings, credit card) or `balances_only` (investment, loan). `BalanceSnapshot` stores one dated balance in minor units per (`account`, `date`, `source`) where source is `simplefin` or `manual`, with optional `ImportBatch` provenance and an optional `note` (manual entry only). Each linked account that receives new rows in a sync gets an `ImportBatch` with source `simplefin` and the remote `simplefin_account_id` of that link. If SimpleFIN reports an error tied to that account (`errlist` `account_id` or `conn_id`) or omits the transaction list, or reports an error naming no account or connection, the app records the error and may store a balance snapshot, but it does not create an active import batch covering cut-over through today, so missing-import warnings stay meaningful. The exception is a `gen.api` item naming no account or connection: the protocol calls it an API-usage error "meant for the developer and not the user", and Bridge sends one whenever the requested window passes 45 days (recommended) or 90 days (capped). It is shown in the sync result but does not hold back imports (#629). Re-syncs skip an active transaction only when it came from a SimpleFIN batch for the same remote account id; CSV and other-source ids, and ids from a previous remote account after a relink, are not treated as duplicates. Disconnect deletes the connection and ciphertext and keeps imported rows. Only the owner can see or manage the connection. While a setup token is being claimed, `SimpleFinClaim` holds the member and a SHA-256 hash of the claim URL, never the token itself. The row is deleted when the claim ends, so a second request with the same token (a double-clicked Connect) is refused before it reaches SimpleFIN instead of getting a 403 that would read as a compromised token (#515). A row older than twice the claim deadline no longer blocks a retry. Connect checks that `FIELD_ENCRYPTION_KEY` is a usable Fernet key before it claims the token; if the key is empty or malformed, no request reaches SimpleFIN and the member is told the token was not used. On an existing connection, an empty or malformed key is treated like a key that cannot decrypt: the sync records and alerts the reconnect message (#572).

**Cut-over (#498, #568).** A transactions-mode link takes rows posted on or after its cut-over date from SimpleFIN, and CSV imports supply the days before it. SimpleFIN dates every row by its posted date, so each side of the cut-over is compared by the day SimpleFIN would give the row, its *cut-over date*: the `Posted Date` of a Capital One row, the `Clearing Date` of an Apple Card row when it is filled in (otherwise its `Transaction Date`), and the one date column of a Huntington, OFX or generic-mapper row. A CSV row whose cut-over date is on or after the link's cut-over previews as invalid ("Covered by SimpleFIN from <date>."). A blank cut-over at link time defaults to the day after the latest cut-over date among the account's active rows; a stored row from a `capital_one` or `apple_card` batch reads its posted date from `original_fields`, and a missing or unparseable one falls back to its `transaction_date`. The cut-over date only decides which source owns a row: a card row still displays and reports under its Transaction Date.

**Bank health, request budget and the Fix/Add pop-up (#694).** Every `/accounts` read (the scheduled sync, Sync now, saving links, the first account-list load, and the Fix and Add checks) stores what it saw in `SimpleFinConnection.last_read`: the time, the listed accounts (id, name, institution, reported type, currency) and, per SimpleFIN connection (`connections[]`, one bank login, joined to accounts by `conn_id`), the bank name, its newest `balance-date`, its account count, and the sanitized `errlist`/`errors` messages that name it (by `conn_id`, by `account_id`, or a plain message that names exactly one bank). Messages that name no bank are kept as connection-wide messages; a `gen.api` notice naming nothing is dropped. Settings -> Connections renders bank health and the link table from this record and makes no live request, except one balances-only read when nothing is stored yet. A bank is stale when its newest balance-date is more than 36 hours old, judged against the current time, so a bank stops looking healthy even without a new read.

SimpleFIN Bridge's developer guide expects "24 requests or fewer per day" per Access Token, replenished through the day, then warnings, then a disabled token. `SimpleFinConnection.request_log` keeps the times of the last 24 hours of `/accounts` requests, and `finance/simplefin_budget.py` records each one before it is sent, under a row lock. The app caps itself at 20 in any rolling 24 hours. Member-started requests (Sync now, link saves, account-list loads, Fix/Add checks and the Cancel sync) stop at 18, keeping 2 for the scheduled sync, which is recorded but never refused. Attempts count, not successes. The page shows "SimpleFIN requests in the last 24 hours: N of 20". Sync now keeps its 15-minute spacing as well.

Fix (shown next to a stale or erroring bank) and Add a bank open SimpleFIN Bridge's home page, `https://bridge.simplefin.org/` (currently redirecting to beta-bridge.simplefin.org), in a pop-up from `window.open` (a tab on iPhone). SimpleFIN documents no per-bank fix or add-institution link, and `connections[].sfin_url` is the server root, so the home page, which lists the member's banks after sign-in, is the most specific documented page. The page opens the pop-up, sets its `opener` to null and only ever reads `closed` or calls `close()`; the Connections response sends `Cross-Origin-Opener-Policy: same-origin-allow-popups` so the pop-up stays reachable. Chromium and WebKit ignore `close()` on a cross-origin pop-up whose opener was cut, so when the window stays open the page shows the outcome, asks the member to close it, and reloads once it is closed (keeping the opener would let the app close it, at the cost of letting Bridge or a bank page in that window navigate the app's tab; an open owner question on #694). The server keeps the flow in the member's session with a baseline (the bank's balance-date and whether it had errors, or the set of known banks for Add). Each check is a full sync, so a successful check has already imported the changes. A flow makes at most 4 requests (checks plus the Cancel sync), at least 60 seconds apart: automatic checks 2 minutes after opening, then 3 and 5 minutes apart, and Done checks at once. A Fix succeeds when the bank has no errors and either had errors before or now has a newer balance-date; an Add succeeds when a bank not in the baseline appears, and its accounts appear in the link table. On success the page closes the pop-up (or asks the member to) and reloads; when the checks run out it says SimpleFIN hasn't refreshed yet and the next sync will pick it up. Cancel, or closing the pop-up, syncs once if the flow and budget allow and no check ran in the last minute. A blocked pop-up shows a normal link instead.

`SimpleFinConnection.health_alerts` holds, per bank, the state ("ok", "stale", "error") last pushed over ntfy. After each stored read and in the daily alert pass, a bank that turns stale or starts reporting an error gets one push on the member's ntfy topic (when ntfy and sync alerts are on), and a later recovery gets one more. The same state is never pushed twice; a state is recorded only once its push is delivered. Pushes name the bank and the Connections link only: never account names, numbers, balances, or SimpleFIN's error text.

## Net worth from balances (issue #69)

Net worth is computed only from `BalanceSnapshot` rows. Transfers, card payments, and investment transactions do not enter the series.

**Sign convention.** Checking, savings, and investment amounts are assets as stored (positive means money held; an overdraft is a negative asset). Credit-card balances are liabilities, and the stored sign depends on source:

- `simplefin` keeps the SimpleFIN protocol value: a negative credit-card balance is money owed. Net worth uses that signed amount, so the owed magnitude subtracts.
- `manual` stores the amount the member typed. For a credit card that is the amount owed as a positive number; an overpayment is negative. Net worth subtracts that stored amount.

- `calculated` (#636) is derived from transactions (see below) and keeps the SimpleFIN protocol sign: a negative credit-card balance is money owed, whichever source the anchor came from.

A manual row never replaces a SimpleFIN row, and a calculated row never replaces either. They can share an account and date because uniqueness includes `source`. On one date the series, the Accounts page, debt payoff, the bills calendar and savings goals all pick `simplefin`, then `manual`, then `calculated` (`net_worth.SOURCE_RANK`), whichever was saved first.

**Calculated past balances (#636).** A newly linked SimpleFIN account has one balance per sync from its link date on, so its earlier imported transactions never reached net worth. On a checking, savings or credit-card account with active transactions, a member who can see the account can open **Calculate past balances** from its balances page (`finance/calculated_balances.py`). Investment, loan and physical-asset accounts are refused (404): their transactions do not explain their value. An account with a balance converted from another currency gets a message instead of a preview, for the reason reconciliation leaves it out (an agent default, not an owner decision). The anchor is the earliest-dated SimpleFIN or manual snapshot (on one date, the one the series would pick), never a calculated one, converted to transaction sign with `signed_balance_minor`. For each calendar month-end M before the anchor date, back to the month of the first active transaction, `balance(M) = balance(anchor) - sum(active transactions dated after M through the anchor date)`, using each transaction's stored date. Transactions of every kind count, as in reconciliation, transfers included because they move money; a split counts once, at its parent amount, because its parts live in `TransactionSplit`. A month with no transactions repeats the previous value. The preview flags a month-end incomplete when any day in its window (after M through the anchor date) has no active, non-manual import batch, reconciliation's coverage rule; since each window ends at the anchor, one gap flags every earlier month-end. Nothing is written until **Save calculated balances**, which recalculates on the server under the account lock and, in one transaction, replaces only that account's calculated rows: unchanged rows stay, changed amounts are updated, and dates no longer produced are deleted, with a `record_created`, `record_edited` or `record_deleted` balance audit event for each. Every calculated date lies before the earliest SimpleFIN or manual row, so none of those is ever written. **Delete calculated balances** removes them all. Calculated rows are not recalculated on their own: after an import is undone or transactions change, calculate again. Forward calculation from the latest real balance is not built.

**Monthly series.** Each month in the selected range uses the last snapshot on or before that month's as-of date (`min` of the calendar month end and the range end). A month with no snapshot for an account carries the last earlier value forward and is flagged carried forward. Months before an account's first snapshot omit that account from totals and flag the month. A month that uses a calculated row shows it with a "calculated" badge and counts it in the month's notes, as it does carried-forward values; carry-forward works the same for calculated rows. Visible accounts are the viewer's private accounts plus household accounts; a household-only filter drops private accounts. Another member's private accounts are never in totals, the chart payload, or errors.

Physical assets and loans (issue #109) use the same snapshot series. Real estate, vehicle, precious metals, and other asset values are manual estimates with an optional note; the UI labels them as estimates, never as appraisals. Precious metals are a single total value, with no quantities or price feeds. Loan balances subtract like credit cards (SimpleFIN protocol sign, or a positive amount owed when entered by hand) and may sync through SimpleFIN in balances-only mode. An optional same-scope pairing (`secured_asset`) shows an equity line (asset value minus loan balance) that does not change totals. Pairing across scopes or owners is rejected so an equity line cannot reveal a value the viewer could not otherwise see.

**Sorting the account lists (#655, migration 0082).** `AccountSortSettings` is one row per member (OneToOne to `Person`, cascades with it and is removed when the member deletes their data) with `net_worth_sort` and `accounts_sort`. Each is blank (the page's own order) or `name_asc`, `name_desc`, `balance_desc` or `balance_asc`, enforced by check constraints. Only the member's own row is read, so another member's choice never changes what they see. Name sorts ignore case and keep equal names in the page's order. Balance sorts use the net-worth value (an amount owed is negative), break ties by name A to Z, and put accounts with no balance last in both directions. The Net worth "By account" panel sorts the latest month's rows (accounts with no balance are not on it); the Accounts page sorts inside each type group and keeps the groups in type order. The choice is saved by a CSRF-checked POST to `account-sort`, which redirects to a fixed page (Net worth keeps only a range that validates).

## Balance reconciliation (issue #535)

`finance/reconciliation.py` checks stored transactions against the institution's own balances. It ignores calculated snapshots (#636): they are derived from the very transactions it checks, so they would always match, and they do not count towards the two snapshot days that make an account without a transactions link eligible. For each account it takes one snapshot per date (SimpleFIN over manual, as net worth does) and converts it to transaction sign with net worth's `signed_balance_minor`: a manual credit-card balance is the positive amount owed, so it is negated; SimpleFIN and every other cash balance is used as stored. Each window (d1, d2] between consecutive dates compares `balance(d2) - balance(d1)` with the sum of active transactions dated after d1 through d2, of every kind. The difference (balance change minus transactions) is kept only for a mismatch and shown only in-app.

Coverage is the union of active import batches other than `manual` (a manual entry covers one row, not a statement period). A SimpleFIN sync batch (one with a remote account id) counts only while that remote account is linked in `transactions` mode or the batch holds a row, because a balances-only link also writes empty batches through today and a batch does not record its link's mode (the same rule as import-due reminders). A window with any uncovered day is `insufficient` whatever its totals. A nonzero difference is `ok-late` when it and the next window's difference sum to zero (`LATE_WINDOWS = 1`); both windows are then `ok-late`. An insufficient window ends that look-ahead. `--since` filters windows ending on or after the date after classification, so a skew pair across the boundary still resolves.

`ReconciliationRun` holds only `ran_at` for the latest scheduled run; older rows are deleted. Alerts use kind `reconciliation`, are always on (like backup alerts), name every mismatched account in `source_accounts` so a recipient who loses sight of one stops seeing the alert, and are raised only when a window mismatches that the recipient was not yet alerted about. `AlertSettings.reconciliation_alerted_windows`, read and written under a row lock so overlapping passes cannot both alert, keeps the alerted windows as `account:start:end` (IDs and dates, no amounts), pruned each run to those still mismatched, so a resolved window that breaks again alerts again and an unresolved one does not re-alert after retention purges its alert row. Because that list decides when to alert, each alert's dedupe key is unique to its run (`reconcile:<run time>:<hash of the current set>`), so a set seen before never collides with an older, already read alert. When a recipient has no visible mismatch left, their reconciliation alerts are deleted.

## Monthly review (issue #95)

`MonthlyReview` stores one computed facts snapshot per member and closed calendar month (`month` is the first of that month). `visibility_key` is a SHA-256 of the viewer's currently visible account ids, current household ids, and visible budget and savings-goal ids with their scopes at generation time. If any of that has changed (for example after leaving a household, or when a household goal or budget becomes private) when the review is opened, the row is rebuilt rather than shown stale. `facts` is JSON of amounts, comparisons, and drill-down links produced from the same report functions as Cash flow, Spending, Budgets, Recurring, Goals, and Net worth. Generation after month close raises one `monthly_review` alert per member with dedupe key `review:<YYYY-MM>`. AI phrasing is not stored on this row. A stored review is not rebuilt when a row in its month is marked or unmarked as an untracked transfer (#642); `has_changed_transfer_marks` finds an `untracked` history row recorded after `generated_at` on a visible row of that month, and the page then says the review may not match Cash flow until it is regenerated, as `has_newer_transactions` does for late imports (#509).
